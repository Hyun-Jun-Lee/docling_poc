# Docling 공식 문서 한국어 가이드

> 이 문서는 Docling 공식 문서의 핵심 내용을 자연스러운 한국어로 재구성한 학습용 안내서다.
> 원문의 코드 예제와 모든 세부 API 목록을 그대로 옮기기보다, 서비스를 설계하고 구현할 때 필요한 개념과 선택 기준을 중심으로 설명한다.
>
> 제외한 문서: Quickstart, FAQ

## 1. 지원하는 입출력 형식

원문: <https://docling-project.github.io/docling/usage/supported_formats/>

Docling은 여러 문서 형식을 하나의 `DoclingDocument` 표현으로 변환한 뒤, 다시 다양한 형식으로 내보내는 문서 변환 도구다. 즉, 입력 파일마다 별도 파서를 다루기보다 변환 이후의 공통 문서 구조를 기준으로 후속 처리, 검색, RAG, 검수 화면을 설계할 수 있다.

### 입력 형식

- PDF
- Office Open XML: DOCX, XLSX, PPTX
- 레거시 Microsoft Office: DOC, XLS, PPT. 이 형식은 LibreOffice가 필요하다.
- OpenDocument: ODT, ODS, ODP
- EPUB, Apple Pages
- Markdown, AsciiDoc, LaTeX, HTML/XHTML, CSV, 일반 텍스트
- 이미지: PNG, JPEG, TIFF, BMP, WEBP
- EBCDIC 고정폭 파일, Docling JSON 등

PDF는 레이아웃, 읽기 순서, 표 구조, 수식, 코드, 그림을 이해하는 고급 파이프라인의 대상이다. 반면 DOCX와 PPTX처럼 이미 구조를 가진 Office 문서는 해당 구조를 활용해 변환한다. 레거시 DOC/PPT는 변환 도구의 설치 여부와 결과 품질을 별도로 검증해야 한다.

### 출력 형식

- Markdown: 사람이 읽거나 RAG 입력으로 쓰기 좋다.
- JSON: `DoclingDocument`의 구조, 좌표, 표, 그림, 계층을 비교적 손실 없이 보존한다.
- HTML, plain text, LaTeX
- DocLang XML 및 DocLang archive
- DocTags: 문서 내용과 레이아웃 특성을 간결하게 표현하는 형식
- JSONL chunks: 검색·임베딩 파이프라인으로 바로 넘길 수 있는 청크 출력

서비스 관점에서는 JSON을 원본에 가까운 보관 형식으로 두고, Markdown이나 JSONL chunk를 검색 및 생성 모델의 입력 형식으로 두는 구성이 일반적이다.

## 2. DOCX와 PPTX: Office 문서 처리

원문: <https://docling-project.github.io/docling/usage/supported_formats/>

원문: <https://docling-project.github.io/docling/v2/>

원문: <https://docling-project.github.io/docling/_generated/examples/run_with_formats/>

DOCX와 PPTX는 Microsoft Office 2007 이후의 Office Open XML 형식이다. Docling은 PDF뿐 아니라 이 형식들을 같은 `DocumentConverter` 진입점으로 변환하고, 결과를 공통 `DoclingDocument`로 제공한다. 따라서 서비스의 후속 저장·검색·검수 계층은 입력 형식에 의존하지 않도록 설계할 수 있다.

그러나 PDF와 Office 문서는 변환 출발점이 다르다. PDF는 페이지 시각 요소에서 텍스트와 구조를 재구성하는 경우가 많아 OCR, 레이아웃 분석, 표 구조 인식의 영향이 크다. DOCX와 PPTX는 파일 안에 문단, 표, 텍스트 상자, 이미지 같은 선언적 구조가 존재하므로 기본 Office 처리 경로는 그 구조를 활용하는 `SimplePipeline`을 사용한다. PDF의 `PdfPipelineOptions`에 있는 OCR, PDF backend, TableFormer 설정을 DOCX/PPTX의 품질 조절 수단으로 생각하면 안 된다.

### DOCX 처리 특성

Word 문서는 보통 제목, 문단, 목록, 표, 그림, 머리글·바닥글처럼 문서 중심의 구조를 갖는다. Docling은 이런 결과를 텍스트·표·그림 및 본문 계층으로 표현한다. 이 구조는 제목 기반 청킹, 표 단위 검색, 본문과 반복 영역의 분리에 특히 유리하다.

서비스에서는 다음을 표본 문서로 확인해야 한다.

- 제목 수준과 본문 계층이 검색용 제목 경로로 충분히 보존되는지
- 중첩 목록, 번호 목록, 표 안의 줄바꿈과 병합 셀이 원하는 출력 형식에서 유지되는지
- 인라인 그림과 캡션, 본문을 벗어난 부유 개체의 순서가 자연스러운지
- 머리글·바닥글·각주 같은 반복 또는 보조 콘텐츠를 본문 검색 대상에 포함할지
- 추적 변경, 주석, SmartArt, 매크로 등 Word 고유 기능을 서비스 요구사항으로 둘 필요가 있는지

특히 표의 병합 구조가 중요한 경우 Markdown만 저장하면 안 된다. JSON 또는 HTML을 기준 결과로 함께 보관해야 한다는 원칙은 DOCX에도 동일하게 적용된다.

### PPTX 처리 특성

PowerPoint는 연속 문단 중심의 문서보다 슬라이드 단위의 시각 자료에 가깝다. 한 슬라이드 안에 제목, 여러 텍스트 상자, 표, 이미지, 도형, 차트가 자유롭게 배치될 수 있다. 따라서 변환 후에는 텍스트가 존재하는지뿐 아니라 슬라이드별 맥락과 읽기 순서가 업무상 자연스러운지를 확인해야 한다.

서비스 검증 시에는 다음을 중점적으로 본다.

- 슬라이드 제목이 이후 텍스트의 문맥을 제공하는지
- 여러 텍스트 상자와 도형 안의 텍스트가 의도한 순서로 이어지는지
- 표·차트·이미지와 인접 설명이 함께 보존되는지
- 회사 공통 템플릿, 장식용 요소, 반복 로고·푸터가 검색 노이즈가 되지 않는지
- 발표자 노트, 애니메이션, 전환 효과, 임베디드 미디어처럼 PPTX 고유 기능이 서비스 요구사항에 포함되는지

마지막 항목들은 지원 여부를 전제로 설계하면 안 된다. 실제 서비스 범위에 필요하다면 해당 버전의 API reference와 대표 샘플로 먼저 변환 결과를 검증해야 한다.

### 형식별 변환 정책

| 구분 | PDF | DOCX | PPTX |
| --- | --- | --- | --- |
| 주된 구조 정보 | 페이지 시각 요소와 내장 텍스트 | 문서의 선언적 구조 | 슬라이드의 선언적 구조와 배치 |
| 주요 설정 관심사 | OCR, 레이아웃, 표 구조, 렌더링 | 본문 계층, 표·그림 보존, 보조 콘텐츠 | 슬라이드 문맥, 텍스트 순서, 시각 요소 문맥 |
| 대표 검수 단위 | 페이지·영역 | 섹션·문단·표 | 슬라이드·요소 묶음 |
| 공통 보관 기준 | Docling JSON, provenance, 품질 상태 | Docling JSON, 계층·표·그림 | Docling JSON, 슬라이드 맥락·요소 순서 |

`DocumentConverter`에서는 `allowed_formats`로 서비스가 받을 형식을 제한하고, 형식별 `format_options`로 별도 정책을 둘 수 있다. 혼합 배치에 PDF, DOCX, PPTX를 함께 넣어도 각 파일은 형식에 맞는 처리 경로로 변환되며, 결과는 공통 API로 다룬다.

### 레거시 Office 형식

DOC, PPT 같은 97-2004 바이너리 형식은 지원되지만 LibreOffice가 필요하다. DOCX/PPTX와 같은 품질·동작을 당연하게 가정하지 말고, 서비스 정책에서 다음 중 하나를 명확히 정해야 한다.

- 업로드 단계에서 DOCX/PPTX로 변환하도록 안내한다.
- LibreOffice 기반 변환을 별도 처리 경로로 운영하고 결과 품질을 분리 측정한다.
- 레거시 형식을 지원 범위에서 제외한다.

## 3. DoclingDocument: 통합 문서 모델

원문: <https://docling-project.github.io/docling/concepts/docling_document/>

`DoclingDocument`는 Docling v2의 핵심 데이터 모델이다. Pydantic 기반 타입으로 구현되어 있으며, PDF·Word·PowerPoint 등 서로 다른 형식의 결과를 공통 구조로 표현한다.

### 콘텐츠 항목

문서의 실제 내용은 항목 유형별 컬렉션에 저장된다.

- `texts`: 제목, 섹션 제목, 문단, 목록 항목, 코드, 수식 등 텍스트 표현이 있는 항목
- `tables`: 표 항목과 그 구조 정보
- `pictures`: 그림 및 그림 관련 정보
- `key_value_items`: 키-값으로 인식된 항목
- `form_items`, `field_regions`, `field_items`: 양식과 필드 관련 항목
- `pages`: 페이지별 정보

이 항목들은 단순히 평평한 목록이 아니다. 각 항목은 부모·자식 참조를 가지며 문서 안에서의 위치와 계층을 표현한다.

### 형식별 예상 생성 항목

`DoclingDocument`의 최상위 스키마는 입력 형식과 무관하게 같다. 예를 들어 `texts`, `tables`, `pictures`, `key_value_items`, `form_items`, `field_regions`, `field_items`, `pages`는 모두 모델에 정의되어 있다. 그러나 이 컬렉션이 실제로 채워지는지는 원본 파일의 내용, 선택한 파이프라인과 옵션, Docling 버전에 따라 달라진다. 빈 배열 또는 빈 맵은 추출 실패가 아니라 해당 항목이 없다는 정상 결과일 수 있다.

아래 표는 기본 처리 경로에서 기대할 수 있는 결과를 정리한 것이다. 이는 형식별 **완전한 필드 계약이 아니라 검수·저장 설계를 위한 예상 범위**다. 서비스에서 필드 존재를 필수 조건으로 삼기 전에, 사용할 Docling 버전과 대표 파일로 JSON 결과를 확인해야 한다.

| 항목 | PDF | DOCX | PPTX |
| --- | --- | --- | --- |
| `texts`와 문서 계층 | 레이아웃 분석·내장 텍스트·OCR 결과로 제목, 문단, 목록, 코드·수식 등이 생성될 수 있음 | 제목, 섹션, 문단, 목록, 텍스트 상자 등의 선언적 구조를 바탕으로 생성될 수 있음 | 슬라이드 제목, 텍스트 상자, 문단, 목록이 생성될 수 있으며 슬라이드 맥락은 그룹·읽기 순서로 표현됨 |
| `tables` | 표 구조 인식이 활성화되고 표가 감지된 경우 행·열·셀 구조가 생성될 수 있음 | Word 표와 병합 셀 구조가 생성될 수 있음 | 슬라이드 표와 셀 구조가 생성될 수 있음 |
| `pictures` | 그림·차트·내장 이미지가 감지 또는 추출될 수 있음 | 인라인/지원되는 그림, 차트·DrawingML 요소는 원본 형식과 렌더링 환경에 따라 결과가 달라질 수 있음 | 그림이 생성될 수 있고, 네이티브 차트는 분류와 표형 데이터를 가진 그림 항목으로 표현될 수 있음 |
| `pages`·좌표·provenance | 페이지와 항목 위치 정보가 핵심 결과이며 검수 UI에 특히 유용함 | 레이아웃·provenance는 제공 가능한 경우에만 포함됨 | 슬라이드가 페이지 단위로 취급되며, 슬라이드 요소의 위치·provenance를 활용할 수 있음 |
| `furniture`와 보조 콘텐츠 | 페이지 머리글·바닥글 등 반복 요소가 분리될 수 있음 | 머리글·바닥글 등 본문 밖 콘텐츠는 원본 구조와 지원 범위를 검증해야 함 | 반복 로고·푸터, 댓글, 발표자 노트 등은 본문 추출을 전제로 가정하지 말고 별도 검증해야 함 |
| `key_value_items`, `form_items`, `field_regions`, `field_items` | 양식·키값 인식 경로 또는 원본 내용에 따라 생성될 수 있음 | 동일 | 동일 |

따라서 저장 스키마는 공통 모델의 모든 컬렉션을 수용하되, 애플리케이션의 필수 필드는 `texts`나 `tables`의 존재가 아니라 변환 상태와 실제 결과 수를 기준으로 판정하는 편이 안전하다. `ConversionResult.confidence`는 `DoclingDocument`의 콘텐츠 필드가 아니라 별도의 변환 품질 신호이므로 함께 보관할 수 있다.

### 레이블별 판단 근거와 한계

`title`, `section_header`, `list_item` 같은 레이블은 공통 `DocItemLabel` 값이다. 따라서 아래 내용은 **해당 레이블을 만들 때 주로 사용하는 근거**이며, 모든 문서에서 같은 레이블이 반드시 만들어진다는 계약은 아니다. 특히 PDF의 기본 레이블은 레이아웃 모델의 분류 결과이므로, 공개 문서만으로는 "이 글꼴이면 title"처럼 완전한 결정 규칙을 만들 수 없다.

| 레이블 또는 항목 | PDF | DOCX | PPTX |
| --- | --- | --- | --- |
| `title` | 레이아웃 모델이 분류한다. 공개된 단순 서식 규칙은 없다. | 문단의 OOXML 스타일 ID가 `Title`일 때 `title`로 처리한다. **굵게·기울임·글자 크기만으로 제목을 판정하지 않는다.** | 텍스트 도형이 `TITLE` 또는 `CENTER_TITLE` 자리표시자일 때 `title`로 처리한다. |
| `section_header`와 제목 수준 | 기본 레이블은 레이아웃 모델이 정한다. 선택 사항인 제목 계층 복원은 북마크/목차 → 번호 체계 → 글꼴 크기(필요 시 굵기·기울임·대문자) 순으로 `section_header`의 **level**을 추론한다. 이 기능은 기본적으로 켜져 있지 않으며, 일반 텍스트를 `title`로 바꾸는 규칙은 아니다. | `w:outlineLvl`이 있으면 이를 우선 사용하고, 없으면 `Heading` 계열 문단 스타일에서 수준을 읽는다. | `SUBTITLE` 자리표시자는 대표적으로 `section_header`가 된다. 일반 텍스트 도형은 보통 문단으로 처리된다. |
| `list_item` | 레이아웃 모델이 분류한다. | OOXML 번호 매기기 정보(`numId`, `ilvl`)를 이용한다. | 도형 자체, 슬라이드 레이아웃, 슬라이드 마스터의 글머리표·번호 매기기 정보를 차례로 확인한다. |
| `table`, `picture` | 레이아웃 모델과 PDF 처리 파이프라인이 표·그림 영역을 검출한다. | OOXML 표와 그림 객체를 구조적으로 읽는다. | 표 도형과 그림 도형을 구조적으로 읽는다. |

DOCX에서 굵게·기울임·글자 크기 같은 값은 `formatting`으로 보존될 수 있지만, 이를 애플리케이션에서 제목 판정의 주 규칙으로 재사용하면 문서 작성자의 임의 서식 때문에 오분류하기 쉽다. 제목 판단이 중요하면 Word의 `Title`/`Heading` 스타일과 개요 수준을 일관되게 적용하는 편이 안전하다. PPTX도 시각적으로 큰 글자보다 제목·부제목 자리표시자를 사용해야 안정적이다.

PDF의 제목 계층 복원은 서식이 있는 디지털 PDF에서 특히 유용하지만, 스캔 OCR 페이지에는 글꼴 메타데이터가 없을 수 있다. 이 경우 북마크·번호 체계가 없으면 시각적 서식 기반 추론의 신뢰도가 낮아질 수 있으므로, 대표 문서로 결과를 검수해야 한다.

원문 및 공식 구현 참고:

- <https://docling-project.github.io/docling/usage/heading_levels/>
- <https://github.com/docling-project/docling/blob/main/docling/backend/msword_backend.py>
- <https://github.com/docling-project/docling/blob/main/docling/backend/mspowerpoint_backend.py>
- <https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/labels.py>

### 문서 구조

- `body`: 본문을 이루는 트리의 루트다. 일반적인 읽기 순서와 섹션 계층은 이 트리에서 확인한다.
- `furniture`: 머리글, 바닥글 등 본문에 속하지 않는 반복 요소를 담는다.
- `groups`: 목록, 장, 인라인 묶음처럼 직접 콘텐츠가 아니라 다른 콘텐츠를 담는 컨테이너다.

본문과 머리글·바닥글을 구분하는 것은 검색 품질에 중요하다. 반복되는 페이지 번호나 회사명이 본문 청크에 매번 포함되면 검색 노이즈가 커질 수 있다. 기본적으로는 `body`를 검색 대상에 사용하고, `furniture`는 별도 보존하거나 필요할 때만 포함하는 편이 좋다.

### 레이아웃과 provenance

항목에 레이아웃 정보가 존재하면 bbox(경계 상자)와 좌표 원점 정보를 통해 문서 내 위치를 추적할 수 있다. provenance는 해당 항목이 원본의 어느 페이지, 어느 영역에서 왔는지를 나타낸다.

이 정보는 다음 기능에 활용할 수 있다.

- 검색 결과에서 원본 PDF의 정확한 페이지와 영역으로 이동
- 사람이 검수할 때 문서 미리보기 위에 인식된 문단·표·그림을 표시
- 표 제목, 그림 설명, 인접 문단을 공간적으로 연결
- 머리글·바닥글 등 반복 요소를 감지하거나 제외
- OCR 또는 레이아웃 인식 오류가 발생한 영역만 재처리

문서 변환 결과를 서비스의 자체 스키마로 정규화하더라도 `kind`, 텍스트, 페이지 번호, bbox, provenance, 부모 계층은 가능한 한 보존하는 것이 좋다.

## 4. 모델 카탈로그: PDF 파이프라인을 이루는 모델들

원문: <https://docling-project.github.io/docling/usage/model_catalog/>

Docling의 PDF 처리 결과는 하나의 모델이 만드는 것이 아니다. 문서의 종류와 설정에 따라 여러 단계가 결합된다. 따라서 품질 문제를 분석할 때도 “Docling 결과가 나쁘다”라고 뭉뚱그리기보다 어느 단계의 문제인지 구분해야 한다.

### 주요 처리 단계

| 단계 | 역할 | 대표 결과 |
| --- | --- | --- |
| 레이아웃 분석 | 페이지 안의 문서 요소를 찾고 분류 | 문단, 표, 그림, 섹션 제목 등의 bbox와 라벨 |
| OCR | 스캔 이미지에서 글자를 인식 | 텍스트와 OCR 품질 정보 |
| PDF 파싱 | 디지털 PDF의 내장 텍스트·도형·이미지를 읽음 | 텍스트 셀, 내장 이미지, 위치 정보 |
| 표 구조 인식 | 표의 행·열·셀 관계를 추론 | 구조화된 표와 셀 내용 |
| 그림 분류·설명 | 그림의 유형을 분류하거나 설명을 생성 | 그림 메타데이터와 캡션 보강 |
| 코드·수식 보강 | 코드 블록이나 수식을 더 정확히 추출 | 코드·수식 표현 |

레이아웃 분석은 문단, 표, 그림, 섹션 제목 같은 요소의 위치와 라벨을 제공한다. 표 구조 인식은 표를 단지 텍스트 덩어리가 아니라 행·열·셀 구조로 만든다. OCR은 이미지 기반 또는 스캔 기반 문서의 글자를 복원한다.

### OCR 엔진과 추론 백엔드

OCR은 자동 선택, Tesseract, EasyOCR, RapidOCR, macOS Vision, SuryaOCR 등의 선택지를 제공한다. 엔진마다 지원 언어, 실행 환경, 속도, GPU 사용 방식이 다르다. RapidOCR은 ONNX Runtime, OpenVINO, PaddlePaddle 등 여러 백엔드를 사용할 수 있다.

서비스를 설계할 때는 문서 종류별로 다음을 평가해야 한다.

- 디지털 PDF와 스캔 PDF의 비율
- 한국어·영어·숫자·표가 섞인 문서의 실제 정확도
- CPU만 사용할지, GPU를 사용할지
- 표 구조 품질이 검색 결과에 미치는 영향
- 모델 다운로드·배포·업데이트 방식

## 5. OCR 엔진

원문: <https://docling-project.github.io/docling/concepts/OCR/>

OCR은 이미지 또는 스캔된 문서에서 문자를 읽어 텍스트로 만드는 단계다. 디지털 PDF에는 이미 텍스트 레이어가 있을 수 있으므로 OCR이 항상 필요한 것은 아니다. 반대로 스캔 PDF는 OCR 품질이 이후 청킹, 검색, 요약의 품질을 크게 좌우한다.

Docling은 여러 OCR 엔진을 지원한다.

- RapidOCR: ONNX Runtime, OpenVINO, PaddlePaddle, Torch 등 여러 백엔드를 선택할 수 있다.
- Tesseract: 널리 쓰이는 범용 OCR 엔진이다. CLI 또는 Python 바인딩 방식으로 연결할 수 있다.
- EasyOCR: 여러 언어를 지원하는 딥러닝 기반 엔진이다.
- OcrMac: macOS의 네이티브 Vision 기능을 활용한다.
- Nemotron OCR, SuryaOCR: 특정 환경과 모델 의존성을 가진 선택지다.

OCR 엔진 선택은 “한국어를 지원하는가”만으로 결정하면 부족하다. 문서 해상도, 글꼴, 표 안의 작은 글자, 도장·서명·손글씨, 세로쓰기, 다단 레이아웃, 비용과 처리량을 실제 샘플로 평가해야 한다.

OCR 결과는 텍스트만이 아니라 위치와 신뢰도까지 제공될 수 있다. 서비스에서는 이 정보를 원본 영역과 연결하고, 낮은 품질의 페이지는 재처리하거나 검수 대상으로 보내는 흐름을 설계할 수 있다.

## 6. Confidence scores: 변환 품질 신호

원문: <https://docling-project.github.io/docling/concepts/confidence_scores/>

Docling은 변환 결과의 신뢰도를 문서 전체와 페이지별로 제공한다. 값은 `ConversionResult`의 `confidence` 필드에서 확인할 수 있다.

점수는 0.0에서 1.0 사이이며, 사람이 판단할 때는 개별 숫자보다 `POOR`, `FAIR`, `GOOD`, `EXCELLENT` 같은 등급을 우선 사용하는 것이 권장된다. 수치 계산 방식과 가중치는 버전에 따라 달라질 수 있다.

### 구성 요소

- `layout_score`: 문서 요소 인식과 레이아웃 분석 품질
- `ocr_score`: OCR로 추출한 내용의 품질
- `parse_score`: 디지털 텍스트 셀 파싱 품질. 문제 구간을 강조하도록 낮은 구간의 영향을 반영한다.
- `table_score`: 표 추출 품질. 문서 시점에 따라 구현 범위를 확인해야 한다.

### 종합 등급

- `mean_grade`: 구성 점수의 평균 관점에서 본 전반적 품질
- `low_grade`: 품질이 낮은 일부 영역을 드러내는 관점의 등급

서비스에서는 이 정보를 다음처럼 활용할 수 있다.

- 낮은 등급 문서는 자동 색인 전에 검수 큐로 전달
- 특정 페이지에만 문제가 있으면 해당 페이지에 다른 OCR 또는 변환 설정 적용
- 문서 유형별 품질 지표를 수집해 파이프라인 설정을 비교
- 검색 결과 화면에서 원본 검토가 필요하다는 상태를 표시

이 기능은 결과의 사실성이나 업무 의미를 보장하는 점수가 아니다. 변환·인식 품질에 대한 기술적 신호로 취급해야 한다.

## 7. 고급 옵션

원문: <https://docling-project.github.io/docling/usage/advanced_options/>

고급 옵션은 `PdfPipelineOptions` 등을 이용해 변환 파이프라인을 제어하는 영역이다. 서비스 수준에서는 문서 유형별 프리셋을 만들고, 변환 요청마다 임의의 복잡한 옵션을 받지 않도록 관리하는 편이 안정적이다.

### 모델과 원격 서비스

기본적으로 필요한 모델은 첫 실행 시 자동으로 내려받을 수 있다. 별도로 모델을 미리 내려받아 `artifacts_path` 또는 `DOCLING_ARTIFACTS_PATH`에 지정하면 해당 경로의 모델을 사용할 수 있다.

Docling은 기본적으로 로컬 모델 실행을 지향한다. 원격 OCR, 그림 설명 API 등 외부 서비스로 문서 데이터를 보낼 수 있는 기능은 명시적인 opt-in이 필요하며, `enable_remote_services=True`로 활성화한다. 서비스에서는 이 값을 전역 기본값으로 열기보다, 데이터 분류와 보안 정책을 확인한 요청에서만 허용하는 것이 적절하다.

### 이미지와 좌표

페이지 좌표는 1인치당 72포인트를 기준으로 한다. 페이지를 이미지로 렌더링할 때의 scale은 문서 포인트당 생성할 픽셀 수에 영향을 준다. OCR·표 추출 품질을 높이기 위해 무조건 큰 이미지를 만들면 메모리와 처리 시간이 크게 늘 수 있으므로, 샘플 문서로 적절한 해상도를 결정해야 한다.

### 표 구조 추출

`do_table_structure` 옵션으로 표 구조 인식을 켤 수 있다. 셀 매칭 방식과 TableFormer의 `FAST`·`ACCURATE` 모드도 조정할 수 있다.

- `FAST`: 처리 속도를 우선한다.
- `ACCURATE`: 복잡한 표에서 정확도를 우선하며 기본 선택지다.

PDF의 실제 텍스트 셀을 표 구조와 다시 매핑하는 과정이 열 병합 오류를 만들 수 있는 경우가 있다. 이때 구조 모델이 예측한 텍스트 셀을 사용하도록 전환하는 옵션을 검토할 수 있다. 이는 만능 해결책이 아니므로, 실제 표 샘플별 비교가 필요하다.

### Native PDF pipeline

`NativePdfPipeline`은 레이아웃, OCR, 표 모델 없이 PDF의 기본 콘텐츠를 읽는다. 원본 텍스트 셀마다 텍스트 항목을 만들고, 내장 이미지는 그림으로 다룬다.

이 파이프라인은 빠르고 모델 의존성이 적지만, 복잡한 레이아웃을 의미 있는 문단·표·제목으로 복원하는 능력은 제한적이다. 디지털 텍스트 PDF의 빠른 처리나 기본 텍스트 추출에는 적합하지만, 구조화 품질이 중요한 문서에는 표준 PDF 파이프라인과 결과를 비교해야 한다.

### 제목 계층 복원

PDF 레이아웃 모델은 섹션 제목을 찾더라도 기본적으로 그 깊이를 모두 같은 수준으로 둘 수 있다. 제목 계층 복원 기능은 PDF 북마크, 번호 체계, 글꼴 스타일을 이용해 제목 수준을 추론한다. 문서 구조 기반 청킹, 목차 생성, 화면 탐색을 제공할 계획이라면 이 기능을 평가할 가치가 있다.

### 서비스 보호 옵션

변환 시 최대 페이지 수와 최대 파일 크기를 제한할 수 있다. 바이너리 스트림도 입력으로 받을 수 있다. CPU 자원은 `OMP_NUM_THREADS` 등으로 제어할 수 있다.

파일 업로드 서비스에서는 요청 시간 제한, 파일 크기 제한, 페이지 제한, 동시 변환 수, 큐잉 정책을 Docling 옵션과 별도로 함께 설계해야 한다.

## 8. 플러그인

원문: <https://docling-project.github.io/docling/concepts/plugins/>

Docling은 플러그인을 통해 기본 제공 옵션 이외의 처리기를 추가할 수 있다. 플러그인은 `pluggy`와 Python packaging entry point를 기반으로 등록된다.

확장할 수 있는 주요 지점은 다음과 같다.

- OCR 엔진
- 레이아웃 엔진
- 표 구조 인식 엔진

### OCR 플러그인

새 OCR 엔진은 `BaseOcrModel`을 구현하고, 이에 대응하는 `OcrOptions` 파생 옵션 클래스를 제공하는 방식으로 추가한다. 플러그인 팩토리는 Docling이 사용할 수 있는 OCR 엔진 목록을 등록한다.

사내 또는 외부 OCR API를 Docling 내부 단계로 편입하고 싶다면 이 구조가 정식 확장 경로다. API 호출, 인증, 파일 또는 페이지 이미지 전달, 응답의 텍스트·bbox·신뢰도 변환을 OCR 모델 구현 안에 캡슐화한다.

다만 서비스 초기에는 별도 OCR 어댑터로 결과를 정규화한 뒤 Docling 후속 처리와 결합하는 접근이 더 단순할 수 있다. Docling 구조 안에 완전히 통합하면 파이프라인 일관성은 좋아지지만, Docling 버전 변화와 플러그인 API를 계속 추적해야 한다.

### 외부 플러그인 사용

서드파티 플러그인은 명시적으로 허용해야 한다. Python API에서는 `allow_external_plugins=True`를 설정하고, CLI에서는 외부 플러그인 허용 옵션을 사용한다. 서비스에서는 허용할 플러그인을 패키지·버전 단위로 관리해야 하며, 임의의 외부 플러그인 자동 로딩은 피하는 편이 좋다.

## 9. 청킹

원문: <https://docling-project.github.io/docling/concepts/chunking/>

청킹은 문서를 검색, 임베딩, 생성 모델 입력에 적합한 단위로 나누는 과정이다. Docling은 단순 Markdown 분할과 네이티브 청커라는 두 접근을 제공한다.

1. `DoclingDocument`를 Markdown 등으로 내보낸 뒤 애플리케이션에서 자체 규칙으로 분할한다.
2. 문서 구조를 직접 사용하는 Docling 청커를 사용한다.

네이티브 청커는 각 청크에 텍스트뿐 아니라 관련 메타데이터를 함께 제공한다. 청크를 임베딩할 때 사용할 문맥화된 문자열도 만들 수 있다.

### 계층형 청커

`HierarchicalChunker`는 문서의 구조 정보를 이용해 요소 단위 청크를 만든다. 기본적으로 목록 항목은 함께 합칠 수 있으며, 제목·캡션 같은 문맥을 청크 메타데이터에 연결한다.

표, 그림, 제목, 문단 같은 문서 요소의 경계를 보존하고 싶을 때 좋은 출발점이다.

### 하이브리드 청커

`HybridChunker`는 계층형 청킹 결과를 토큰 길이에 맞게 다시 조정한다.

- 모델의 최대 토큰 수를 넘는 청크는 분할한다.
- 같은 제목과 캡션 문맥을 공유하는 작은 연속 청크는 합칠 수 있다.
- 여러 청크로 나뉜 표에는 표 헤더를 반복해 각 조각의 의미를 유지할 수 있다.

임베딩 모델과 동일한 토크나이저를 청커에 연결하는 것이 중요하다. 문자 수 기준으로 자르는 방식은 한국어·영어·표·코드가 섞인 문서에서 실제 모델 토큰 수와 차이가 커질 수 있다.

### 줄 기반 토큰 청커

`LineBasedTokenChunker`는 줄 경계를 최대한 유지한다. 표, 코드, 로그, 목록처럼 줄 단위 구조가 중요한 콘텐츠에 유용하다. 필요하면 각 청크 앞에 표 헤더 같은 반복 접두사를 붙일 수 있다.

### 서비스에서의 권장 원칙

- 청크에는 원문 텍스트만 저장하지 말고 문서 ID, 페이지 번호, 항목 유형, 제목 경로, bbox 또는 원본 참조를 함께 저장한다.
- 표는 문단처럼 임의 분할하지 말고 행·열·헤더 문맥을 보존한다.
- 검색용 청크와 사용자에게 보여줄 원문 단위는 같을 필요가 없다.
- 청크 전략을 고정하기 전에 실제 질의와 실제 문서로 검색 품질을 측정한다.
- 문서 구조가 충분히 보존되는 경우에는 구조 기반 청킹을 우선 검토하고, 최종 길이 조절은 토큰 기반으로 수행한다.

## 10. 아키텍처: 변환기, 백엔드, 파이프라인의 역할

원문: <https://docling-project.github.io/docling/concepts/architecture/>

Docling의 변환 흐름은 다음과 같이 이해하면 된다.

```text
입력 문서
  -> DocumentConverter
  -> 형식별 backend
  -> pipeline
  -> ConversionResult
  -> DoclingDocument
  -> 직렬화 / 청킹 / 후속 서비스 처리
```

`DocumentConverter`는 입력 형식을 판별하고, 해당 형식에 어떤 backend와 pipeline을 사용할지 조합하는 진입점이다. PDF뿐 아니라 DOCX, PPTX 등 여러 형식을 같은 인터페이스로 다룰 수 있게 해 준다.

backend는 원본 형식에서 기초 정보를 읽는다. 예를 들어 PDF backend는 내장 텍스트, 페이지, 이미지 같은 원시 요소를 읽는다. pipeline은 이 결과를 기반으로 OCR, 레이아웃 분석, 표 구조 인식, 보강 작업을 어떤 순서로 수행할지 조정한다.

이 구분은 서비스 설계에서 중요하다. PDF 결과에 문제가 생겼을 때, 원본 텍스트를 읽지 못한 backend 문제인지, OCR 문제인지, 레이아웃·표 모델 문제인지 분리해서 진단할 수 있기 때문이다. `DocumentConverter`를 서비스의 도메인 모델로 직접 노출하기보다는, 변환 어댑터 내부에 두고 `ConversionResult`와 `DoclingDocument`를 정규화된 내부 모델로 변환하는 경계를 두는 편이 장기적으로 관리하기 쉽다.

## 11. 직렬화: 같은 문서라도 출력 형식마다 보존되는 정보가 다르다

원문: <https://docling-project.github.io/docling/concepts/serialization/>

직렬화는 `DoclingDocument`를 Markdown, HTML, JSON, DocTags 같은 텍스트 형식으로 바꾸는 과정이다. `export_to_markdown()` 같은 편의 메서드는 내부적으로 해당 형식의 serializer를 사용한다.

중요한 점은 출력 형식이 문서 구조를 같은 수준으로 보존하지 않는다는 것이다. 특히 병합 셀이 있는 표가 대표적이다.

| 출력 형식 | 병합 셀 정보 |
| --- | --- |
| JSON | 행·열 병합 정보가 보존된다. |
| DocLang, DocTags | 표 구조를 표현하는 방식으로 보존된다. |
| HTML | `rowspan`, `colspan`으로 보존된다. |
| Markdown | 표준 문법의 한계로 병합되지 않은 형태로 평탄화된다. |
| LaTeX | 현재 기본 출력에서는 병합 구조가 평탄화될 수 있다. |

따라서 “사용자가 읽을 결과”와 “서비스가 보관할 기준 데이터”를 구분해야 한다. Markdown은 읽기와 검색에 편하지만, 정확한 표 구조나 bbox를 기준으로 후속 처리를 해야 한다면 JSON을 기준 원본으로 보관해야 한다. 병합 헤더가 중요한 표를 HTML이나 별도 표 데이터로 제공할지도 이 단계에서 결정한다.

Docling은 문서 전체뿐 아니라 텍스트, 표, 그림, 목록 등 구성 요소별 serializer도 제공한다. 특정 도메인에 맞는 표 표현이나 그림 placeholder 정책이 필요하면 serializer 확장도 검토할 수 있다.

## 12. 변환 실행과 대량 처리: 성공만 있는 작업이 아니다

원문: <https://docling-project.github.io/docling/_generated/examples/custom_convert/>

원문: <https://docling-project.github.io/docling/_generated/examples/batch_convert/>

단일 변환은 `DocumentConverter.convert()`로, 여러 문서는 `convert_all()`을 통해 처리할 수 있다. 대량 변환에서는 문서별 성공 여부를 따로 다뤄야 한다.

- `SUCCESS`: 문서 변환이 성공했다.
- `PARTIAL_SUCCESS`: 일부 콘텐츠 또는 단계에서 오류가 있었지만 결과가 생성되었다. 오류 목록을 보관하고, 검색 색인 포함 여부를 정책으로 결정해야 한다.
- 실패: 변환 결과가 없거나 신뢰할 수 없으므로 재시도 또는 검수 대상으로 보낸다.

대량 처리 서비스는 성공한 결과만 저장하는 방식으로 끝나면 운영 상태를 파악하기 어렵다. 원본 파일 식별자, 변환 요청 시각, Docling 버전, 선택한 pipeline 옵션, 상태, 오류 정보, 품질 등급, 출력 경로를 작업 이력으로 남겨야 한다. 그래야 특정 모델이나 옵션 변경 뒤에 품질이 바뀌었는지 추적할 수 있다.

공식 예제는 하나의 변환 결과에서 JSON, HTML, Markdown, 텍스트, DocTags, YAML을 각각 출력하는 방식도 보여 준다. 처음에는 여러 표현을 함께 저장해 비교하고, 서비스 정책이 안정되면 필요한 산출물만 유지하는 방식이 좋다.

## 13. Enrichment와 VLM: 기본 변환 결과에 의미를 추가하는 단계

원문: <https://docling-project.github.io/docling/usage/enrichments/>

원문: <https://docling-project.github.io/docling/usage/vision_models/>

기본 변환 이후 선택적으로 실행할 수 있는 보강 단계가 있다. 이 기능들은 보통 추가 모델 추론이 필요하므로 기본값으로는 꺼져 있다.

- 코드 이해: 코드 블록을 더 정확한 코드 표현으로 보강한다.
- 수식 이해: 수식으로 분류된 텍스트를 보강한다.
- 그림 분류: 그림을 차트, 다이어그램, 자연 이미지 등으로 분류한다.
- 그림 설명: 그림이나 도표를 자연어로 설명한다.

그림 설명은 이미지가 많은 보고서에서 검색성과 질의응답 품질을 높일 수 있다. 다만 모델이 생성한 설명은 원본 텍스트와 달리 생성 결과이므로, 원문 추출값과 같은 신뢰 수준으로 취급하면 안 된다. 서비스 데이터 모델에는 `source_extracted`와 `model_generated` 같은 출처 구분을 두는 것이 바람직하다.

`VlmPipeline`은 페이지 전체를 비전 언어 모델로 변환하는 별도 경로다. DocTags, Markdown, HTML 같은 결과를 만들 수 있으며, 일반적인 PDF 파이프라인과 품질·속도·비용·재현성의 특성이 다르다. 표준 PDF 파이프라인이 어려워하는 서식이나 복잡한 시각 문서를 대상으로 비교 후보가 될 수 있지만, 기본 경로를 대체하기 전에 문서군별 평가가 필요하다.

## 14. API server: Docling을 공용 변환 서비스로 운영하는 방법

원문: <https://docling-project.github.io/docling/usage/api_server/>

원문: <https://docling-project.github.io/docling/usage/api_server/deployment/>

원문: <https://docling-project.github.io/docling/usage/api_server/rest_api/>

Docling은 Python 라이브러리로 애플리케이션 프로세스 안에서 직접 실행할 수 있고, `docling-serve`를 통해 HTTP 변환 서비스로 실행할 수도 있다.

| 방식 | 적합한 경우 |
| --- | --- |
| Python 라이브러리 | 하나의 Python 서비스 안에서 변환을 호출하고 설정을 코드로 세밀하게 제어할 때 |
| API server | 여러 서비스·언어가 하나의 변환 기능을 공유해야 할 때 |
| Jobkit | 대규모 또는 분산 배치 변환이 필요할 때 |
| MCP server | AI 에이전트에 문서 변환 도구를 제공할 때 |

API server는 동기 또는 비동기 변환 요청을 제공한다. 비동기 요청은 작업 ID를 받고, 상태를 polling하거나 WebSocket으로 받아 완료 후 결과를 조회한다. 긴 PDF나 다수의 문서를 다루는 웹 서비스에서는 업로드 요청을 기다리게 하기보다 비동기 작업 모델을 우선 검토하는 편이 자연스럽다.

단일 노드에서는 로컬 실행 엔진으로 시작할 수 있고, 처리량을 확장해야 하면 Redis 기반 RQ 엔진으로 API와 변환 worker를 분리할 수 있다. 이 구조를 사용할 때는 API가 작업을 받는다고 해서 변환이 자동으로 실행되는 것이 아니며, 실제로 작업을 수행할 worker가 별도로 실행되어야 한다.

서비스화할 때 먼저 정해야 할 정책은 다음과 같다.

- 파일·페이지 수 제한과 허용 형식
- 동시 작업 수, 대기열, 재시도, 시간 제한
- API 인증과 결과물 보관 기간
- 이미지 출력 방식: placeholder, embedded, referenced
- pipeline 옵션을 사용자에게 어느 범위까지 노출할지
- 변환 결과, 오류, 품질 등급, 원본 참조를 어떤 데이터 모델로 저장할지

## 다음 학습 순서

전체 서비스를 염두에 둔다면 다음 순서가 자연스럽다.

1. PDF, DOCX, PPTX의 형식별 처리 특성과 `DoclingDocument` 구조를 이해한다.
2. 직렬화별 정보 손실 차이와 기준 보관 형식을 결정한다.
3. PDF 파이프라인의 backend·레이아웃·OCR·표 구조 단계를 구분한다.
4. 고급 옵션으로 문서 유형별 변환 정책을 설계한다.
5. Confidence score와 변환 상태를 이용한 품질 관리 흐름을 정의한다.
6. 청킹과 검색 인덱스 스키마를 설계한다.
7. 그림·수식·코드 보강과 VLM 변환이 필요한 문서군을 평가한다.
8. 서비스 경계가 필요해지면 API server와 비동기 작업 구조를 검토한다.
9. 기본 기능으로 부족한 OCR·레이아웃·표 처리가 확인될 때 플러그인을 검토한다.

공식 문서는 수시로 바뀔 수 있으므로, 실제 구현 시에는 본 문서의 각 원문 링크와 해당 버전의 API reference를 함께 확인한다.
