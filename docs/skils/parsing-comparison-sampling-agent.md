# Tika·Docling 파싱 비교 샘플링 에이전트 지침

> 현재 보고서에서는 샘플 비교 카드 영역을 제거했다. 이 지침으로 만든 카드 JSON은
> 보조 검토 자료로 보관하며, 아래에 설명된 보고서 불러오기·자동 반영은 현재 지원하지 않는다.

이 문서는 사내망의 GLM-5.3-Flash 에이전트에게 전달할 작업 지침이다.
에이전트의 역할은 대표 구간 선정과 원본 증거 수집이며, 기능별 비교 카드는 수집한 증거를 기반으로 생성한다.

## 역할과 목표

당신은 Apache Tika와 Docling의 문서 파싱 결과를 비교하기 위한 분석 에이전트입니다.

목표는 같은 문서의 대표 구간을 선정하고, 두 도구가 제공하는 정보의 차이를 HTML의 기능별 비교 카드로 보여줄 수 있도록 자료를 추출하는 것입니다.

## 1. 입력 자료와 사용할 파일

비교 실행 결과 폴더의 `manifest.json`을 읽어 문서와 실행 결과 경로를 확인하세요.
폴더 번호나 파일명을 고정해서 가정하지 마세요.

| 자료 | 용도 |
|---|---|
| 입력 원본 PDF·DOCX·PPTX | 실제 내용·서식·배치 확인 |
| `manifest.json` | 문서 ID·이름·해시, 도구별 회차·상태·결과 경로 확인 |
| Docling `raw.json.gz` | 구조·서식·관계·위치 정보의 원본 증거 |
| Docling `content.md` | 내용 탐색 및 Markdown 표현 확인 |
| Tika `tika-output.json` 또는 `raw.json.gz` | 문서·내장 리소스별 내용과 메타데이터의 원본 증거 |
| Tika `content.md` | 최상위 문서의 Markdown 표현 확인 |

`snapshot.json`은 일부 속성을 제외한 비교용 데이터이므로 기능 제공 여부의 최종 근거로 사용하지 마세요.

각 도구의 **첫 완전 성공 회차**를 기본으로 선택하고 실제 회차 번호를 기록하세요.
성공 결과가 없으면 부분 성공 여부를 명시하세요.

문서 원본을 직접 확인할 수 없다면 선정 결과를 **“추출 결과 기반 후보”**로 표시하고,
원본 대비 정확도를 판정하지 마세요.

## 2. 샘플링할 구간

문서당 3~5개의 대표 구간을 우선 선정하세요.
여러 문서에 같은 사례가 반복되면 서로 다른 기능 차이가 드러나는 사례를 우선하세요.

| 카드 유형 | 선정할 구간 | 함께 포함해야 할 내용 |
|---|---|---|
| 제목·본문 | 제목과 이어지는 본문 | 제목, 본문 1~2개, 가능하면 다음 제목 경계 |
| 목록 | 번호·기호가 있는 연속 항목 | 목록 도입문, 연속 항목 2~4개, 중첩 목록이 있으면 상·하위 항목 |
| 서식 | 굵기·기울임·밑줄 등이 섞인 문장 | 강조 부분과 앞뒤 일반 텍스트 |
| 표 | 헤더·병합 셀·단위 등이 있는 표 | 헤더, 비교할 행·셀, 단위, 관련 주석 |
| 그림·캡션 | 그림과 제목·설명이 함께 있는 구간 | 그림 항목, 캡션, 관련 설명 |
| 본문·머리글 구분 | 본문과 반복 머리글·바닥글이 인접한 구간 | 본문과 해당 머리글·바닥글 |
| 원본 위치 | 원본에서 위치를 명확히 확인할 수 있는 짧은 구간 | 텍스트 또는 표·그림과 위치 정보 |

원본에 없는 유형을 억지로 선정하지 마세요.
일반적인 성공 사례와 차이가 드러나는 사례를 함께 포함하세요.

두 도구에서 **같은 원본 내용을 가리키는 구간**을 선택하세요.
블록 번호나 텍스트 항목 개수는 서로 일치하지 않아도 됩니다.
한쪽 항목 하나가 다른 쪽에서는 여러 항목으로 나뉠 수 있습니다.

## 3. Docling 원본에서 추출할 부분

원본 JSON이 `document`로 감싸져 있으면 그 내부를 문서 본문으로 사용하세요.
감싸져 있지 않은 형식도 처리하세요.

| 카드 유형 | 원본에서 가져올 정보 |
|---|---|
| 제목·본문 | 해당 `texts` 항목의 `self_ref`, `label`, `text`, `level`, `parent`, `children`, `prov` |
| 목록 | 관련 `groups` 항목과 소속 텍스트의 `label`, `marker`, `enumerated`, 부모·자식 참조 |
| 서식 | 해당 텍스트 항목들의 `text`, `orig`, `formatting`, 필요하면 `hyperlink` |
| 표 | 해당 `tables` 항목의 `data`, 행·열 수, 비교 셀의 텍스트·행열 위치·병합·헤더 속성, `captions`, `footnotes`, `prov` |
| 그림·캡션 | 해당 `pictures` 항목의 참조·위치·캡션·주석과 연결된 텍스트 항목 |
| 본문·머리글 구분 | 해당 항목의 `label`, `content_layer`, `body` 또는 `furniture`에서의 연결 |
| 원본 위치 | `prov`에 실제 존재하는 `page_no`, `bbox`, `charspan`과 원본 문서 식별 정보 |

**참조만 복사하지 말고 관계를 설명하는 데 필요한 대상 항목도 함께 가져오세요.**

예를 들어 `parent={"$ref":"#/groups/3"}`이 있으면 다음을 함께 수집합니다.

- 선택한 텍스트 항목
- `groups/3`의 실제 객체
- 그 그룹에서 비교 구간에 해당하는 자식 항목
- 그룹 전체 자식 수와 이번에 포함한 자식 수

문서 전체 참조를 무제한으로 확장하지 마세요.
생략한 참조가 있으면 표시하세요.

`groups`를 모두 의미적 섹션으로 해석하지 마세요.
`inline`, `list`, `chapter` 등 실제 종류를 유지하세요.
`bold:true`만으로 제목을 새로 분류하지 마세요.

## 4. Tika 원본에서 추출할 부분

재귀 JSON의 각 객체를 문서 또는 내장 리소스 단위로 확인하세요.

| 카드 유형 | 원본에서 가져올 정보 |
|---|---|
| 제목·본문 | 해당 리소스의 `tk:content` 안에서 제목 표기와 뒤따르는 본문 |
| 목록 | 번호·기호·들여쓰기·중첩을 포함한 원문 구간 |
| 서식 | `**…**` 등 실제 출력에 남아 있는 서식 표기 |
| 표 | 헤더·구분선·셀을 포함한 Markdown 또는 HTML 표 원문 |
| 그림·캡션 | 그림 관련 출력 구간과 관련 내장 리소스 객체의 메타데이터 |
| 본문·머리글 구분 | 해당 텍스트 구간과 실제로 제공된 구분 표기 |
| 원본 위치 | 실제 출력에 있는 파일·리소스·페이지·위치 관련 메타데이터 |

버전에 따라 `X-TIKA:content` 등 다른 키가 사용될 수 있으므로 실제 키 이름을 확인하세요.

각 발췌에는 다음 출처를 남기세요.

- 원본 파일 경로
- 리소스 배열 인덱스
- 내용 필드 이름
- 리소스 이름과 MIME 타입
- 발췌한 원문
- 가능하면 내용 문자열 내 시작·끝 위치: Python 문자열 인덱스 기준, 끝 위치 제외 방식

Markdown의 공백·줄바꿈·기호를 수정하거나 보기 좋게 재작성하지 마세요.

**Markdown 제목이 실제 본문 제목인지 확인하세요.**
내장 이미지 파일명이 `# image1.png`처럼 제목으로 출력될 수 있습니다.
리소스 이름과 본문 제목을 혼동하지 마세요.

Tika의 내장 리소스 깊이를 본문의 제목·목록 계층으로 해석하지 마세요.

## 5. 비교 카드에 필요한 정보

각 카드에는 다음 정보를 준비하세요.

| 카드 영역 | 필요한 내용 |
|---|---|
| 식별 정보 | 카드 ID, 유형, 문서 ID·이름·해시, 각 도구의 회차 |
| 선정 이유 | 이 구간에서 어떤 기능 차이를 확인하려는지 |
| 원본 구간 | 원본 위치와 해당 내용에 대한 짧은 설명 |
| Docling 증거 | 관련 원본 JSON 객체·참조와 Markdown 발췌 |
| Tika 증거 | 관련 리소스의 메타데이터와 내용 발췌 |
| 속성 비교 | 분류·수준·서식·그룹·표 구조·위치 등 카드 유형에 맞는 항목 |
| 후속 처리 | 직접 조회 가능, Markdown 해석 필요, 관계 추론 필요 등 |
| 검토 사항 | 대응 불확실성, 참조 생략, 원본 확인 필요 사항 |

속성의 제공 상태는 다음처럼 구분하세요.

- **명시적 필드:** JSON 속성으로 직접 제공
- **출력 마크업:** Markdown·HTML 표기로 제공
- **파생 해석:** 순서·표기 등을 이용해 분석 과정에서 구성
- **발췌에 없음:** 이번에 수집한 구간에는 없으며 전체 출력 여부는 미확인
- **현재 결과에 미제공:** 관련 원본 출력까지 확인했지만 제공되지 않음
- **판단 불가:** 자료 부족 또는 구간 대응 불확실

필드 누락, `null`, 빈 배열, `false`를 같은 상태로 취급하지 마세요.

## 6. 카드 설명의 작성 예시

다음은 형식을 설명하기 위한 예시이며 실제 관찰 결과가 아닙니다.

> 카드: 목록 구조  
> 선정 이유: 같은 조건 목록을 각 도구가 어떤 형태로 표현하는지 확인
>
> Docling 증거: `label=list` 그룹과 `list_item` 자식 참조 제공  
> Tika 증거: 연속된 Markdown 목록 표기 제공, 해당 출력에 그룹 객체 없음
>
> 후속 처리 차이:  
> Docling은 그룹 참조를 따라 목록 항목을 조회할 수 있음.  
> Tika는 Markdown을 해석해 목록 항목과 소속 구조를 구성해야 함.
>
> 검토 범위: 이 구간의 구조 표현 차이이며, 목록 내용의 정확도를 판정한 결과는 아님.

이 설명은 실제 증거가 있을 때만 작성하세요.
해당 도구가 일반적으로 지원한다는 이유로 현재 출력에 없는 속성을 채우지 마세요.

## 7. 최종 산출물

다음 두 가지를 작성하세요.

1. **샘플링 목록:** 문서별 선정 구간, 카드 유형, 선정 이유, 대응 확실성, 원본 확인 여부
2. **카드 데이터 JSON:** 위 카드 영역의 정보를 카드별로 구조화한 자료

카드 데이터는 프로그램이 읽어 HTML을 생성할 수 있도록 작성하세요.
원본 발췌와 에이전트의 설명을 별도 필드에 보관하세요.

그림의 base64 데이터 전체는 카드 JSON에 복제하지 말고 원본 참조를 남기세요.
문서 파싱 결과와 기존 실행 기록은 수정하지 마세요.

**성공 기준은 각 카드에서 원본 증거를 추적할 수 있고,
두 도구가 제공하는 정보와 후속 처리의 차이를 설명할 수 있는 것입니다.**
원본 확인 없이 도구의 우열이나 정확도 점수를 산출하지 마세요.

## 8. 보고서가 읽는 카드 JSON 형식

카드 데이터 JSON은 [기능별 비교 카드 입력 규격](../feature-cards-guide.md)의
`docling_poc.feature_cards`, 버전 `1`을 따르세요. 임의의 필드 이름으로 출력하지 마세요.

- 문서 ID·SHA-256과 회차는 `manifest.json`에서 읽으세요.
- `docling.content`와 `tika.content`에는 각 도구의 원본 발췌를 **문자열**로 넣으세요.
  JSON 항목은 JSON 문자열로 직렬화하고, `format`은 `json`으로 지정하세요.
- 필요한 관련 그룹·항목은 Docling의 `{"items": [...]}` 형태로 함께 수집할 수 있습니다.
- 원본 참조·리소스 인덱스·문자 범위는 각 증거의 `source_refs` 문자열 배열에 기록하세요.
- 선정 이유는 `reason`, 원본 위치는 `source_location`, 분석 설명·불확실성은 `note`에 넣으세요.
- `original_checked`는 실제 원본 확인 여부를 기록하며, 확인하지 않은 경우 `false`로 지정하세요.
- 원본 증거와 에이전트의 분석 설명은 섞지 마세요. 화면의 속성 요약은 원본 발췌에서 계산합니다.

완성된 파일은 보고서의 **카드 JSON 불러오기**로 불러오거나, 출력 폴더의
`feature-cards.json`으로 보관한 뒤 HTML을 다시 생성하면 됩니다.
